# Content process sandbox

The Windows content process uses an AppContainer with no OS network capabilities and a strict Job Object. The per-capability base suite passes locally; CI runs the same twelve rows, and issue #526 closes only after the exact pushed commit passes. These checks establish the Windows process boundary; feature-specific backend acceptance remains in the corresponding feature issues.

The original contract in [the scripting design](study/17-scripting.md) requires an AppContainer without direct network access, a Job Object with hard memory and CPU limits, child-process and desktop restrictions, explicitly brokered resources, and a watchdog that retains the last frame with a visible stopped notice.

Containment is established while the child is suspended, before its primary thread resumes. A failed security setup rejects the launch. Each content process receives a unique AppContainer identity; replacing a document inside that process retires its document runtime. The job has a 256 MiB default hard memory cap, a 25% default CPU hard cap, one active process, kill-on-close and desktop/clipboard restrictions. The launch handle list contains only the three standard pipes. The environment contains the trusted runtime location and private profile paths, without arbitrary inherited host credentials. Windows uses a headless apphost so startup does not require changing the user's console policy.

Only deployed code/runtime directories receive read/execute access when existing application-package permissions do not already provide it. The frame directory receives traverse access and its specific host-created frame file receives read/write access with a low-integrity label. No workspace or user-data directory receives a recursive grant. Cross-process and cross-user ACL updates are serialized; cleanup removes only the launch's own identity entries. Cleanup failures are traced. Security profiles and job handles retire with the process.

The host chooses and holds the shared frame file before launch. Frame messages must match its path, dimensions and stride before dispatch. A child-provided path or malformed descriptor cannot redirect the host to another file. Frame dispatch and queued UI work are checked against the currently attached process and generation. Frames, capture activity and stop notices arriving before the control handle exists are retained and flushed on the owning UI thread. After termination, the control paints retained pixels and the stopped notice together, including a notice when no first frame was delivered.

The view owns its attached client. Replacing it retires the old process after releasing its frame mapping, while preserving the already copied bitmap until a new frame arrives. Reattaching the same client preserves pending state. Switching to static rendering retires the process and removes its stopped notice. Client disposal releases all owned resources even if a host message callback faulted; the original callback failure remains observable.

Verification uses a separate trusted native probe executable to test direct OS access. It boots the same document runtime as ContentHost before checking the token, integrity level, zero OS capability SIDs, actual job configuration, host-file read/write denial, sockets, child creation, hard memory termination, watchdog termination and forged frame descriptors. The network check first proves the parent can reach the same loopback listener; an AppContainer attempt must be denied or blocked without a pending connection. Actual ContentHost/WinForms tests cover applied grants, feature operations, retained pixels and the painted notice. Separate real-process regressions cover pre-handle frame and stop delivery, including the event's owning thread.

The Windows CI matrix includes all ten grants (`webgl`, `media`, `sound`, `camera`, `microphone`, `workers`, `webassembly`, `iframes`, `webrtc`, `service-workers`), a denied row and an all-granted row. Every row runs the native base suite and the rendered watchdog checks. Camera/microphone operations exercise the existing synthetic compatibility implementation, and service-worker registration uses a brokered fixture. The sound grant is checked as applied; the unsupported audio fixture must reject playback. Real sound output through process IPC is still absent, so this fixture does not prove it. Feature-specific sandbox cases join their row as their original feature issue reaches acceptance.

The WinForms lifecycle scenarios run serially, and the full CI suite runs one test executable at a time. Cold-starting unrelated content processes concurrently on a small runner can consume the watchdog's wall-clock budget before the first frame; the supervisor now allows a bounded startup-only grace window before the first heartbeat, then applies the configured deadline strictly. Serialization still isolates the scenario under test. A one-CPU run reproduced three UI failures before the correction and passed all eight cases afterward.

Authoritative Windows API references: [AppContainer launch](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [CPU rate control](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information), and [desktop restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions).

This work does not establish real camera/network transport, timed media, native GPU or WebAssembly execution, or completion of the other original milestone 6 issues. The non-Windows launch path still needs its own OS containment design; the original #526 matrix targets Windows.
