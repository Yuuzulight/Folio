Driftwood

A small, fast task runner for monorepos. One config file, no daemon.

buildpassing version2.4.1 licenseMIT

Driftwood reads a single drift.toml at the root of your repository, works out which packages changed since the last run, and runs only the tasks that need to run, in dependency order, in parallel where it can. On our own 140-package repository it cut average CI time from 19 minutes to 4 minutes 40 seconds.

Installation

Driftwood ships as a single binary. Pick whichever install method suits you:

  1. Download a prebuilt binary from the releases page and put it on your PATH.
  2. Or build it from source:
    1. Clone the repository.
    2. Run ./scripts/build-release in the root.
    3. Copy target/driftwood somewhere on your PATH.

Check that it worked:

$ driftwood --version
driftwood 2.4.1 (built 2026-08-14)

Quick start

Create a drift.toml next to your top-level packages folder:

[workspace]
packages = ["packages/*", "apps/*"]

[task.build]
run     = "./scripts/build"
depends = ["^build"]      # build dependencies first
outputs = ["dist/**"]

[task.test]
run     = "./scripts/test"
depends = ["build"]

Then run a task across the whole workspace:

$ driftwood run test
  planned 38 tasks (22 cached, 16 to run)
  ok  packages/core       build  3.1s
  ok  packages/core       test   5.8s
  ok  apps/dashboard      build  7.4s
  ...
  done in 41.2s

Tip

Press Ctrl + C once to stop scheduling new tasks and let running ones finish. Press it twice to stop immediately.

Configuration reference

Every task accepts the following keys:

KeyTypeDefaultDescription
runstring—The shell command to execute.
dependslist[]Tasks that must finish first. A leading ^ means "in dependency packages".
inputslist["**"]Files whose contents form the cache key.
outputslist[]Files restored on a cache hit.
envtable{}Extra environment variables. These also affect the cache key.

Command-line flags

  • --filter <glob> — only run tasks in matching packages.
  • --since <ref> — only consider packages changed since a revision.
  • --concurrency <n> — maximum parallel tasks (default: number of CPU cores).
  • --no-cache — ignore the cache for this run.
    • Outputs are still written to the cache afterwards.
    • Combine with --dry-run to see what would run.

Caution

If a task writes files that are not listed in outputs, those files will be missing after a cache hit. This is the most common cause of "works locally, fails in CI" reports.

FAQ

Does Driftwood need a background process?

No. Every run starts from scratch and reads the cache from .drift/cache. There is nothing to restart when you switch branches.

Can I share the cache between machines?

Yes. Set cache.remote to any HTTP endpoint that supports GET and PUT. Entries are content-addressed, so a shared cache is safe for concurrent writers.

How do I see why a task was not cached?

Run with --explain. Driftwood prints the inputs that changed and their old and new hashes.
