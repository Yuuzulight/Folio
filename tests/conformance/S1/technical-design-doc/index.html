Context and problem

Beacon ingests about 2.3 billion events per day from customer websites and apps. Every event is currently written to a single cluster of SSD-backed columnar nodes and kept there for the full retention period, which is 13 months for most plans. Storage now accounts for 61% of our infrastructure bill, up from 38% eighteen months ago.

Query logs tell a clear story: 94% of queries touch only the last 30 days, and fewer than 1% reach back further than 90 days. We are paying premium storage prices for data that is almost never read.

"We keep a year of data on the fastest disks we own so that a handful of customers can run their annual report once." — Q2 infrastructure review

Goals and non-goals

Goals

  • Cut storage cost per retained event by at least 50% within two quarters.
  • Keep p95 latency for queries over the last 30 days under 800 ms.
  • Allow queries over older data, accepting latency of up to 10 s.

Non-goals

  • Changing the event schema or the ingestion API.
  • Reducing the retention period offered to customers.
  • Real-time queries over data older than 30 days.

Proposed design

Events move through three tiers as they age. A background compaction pipeline rewrites data into larger, more compressed files as it moves down. A thin routing layer in front of the query service decides which tiers a query needs based on its time range.

Storage tiers

TierAgeMediumCost / TB-monthTarget p95
Hot0–30 daysLocal NVMe$92.00400 ms
Warm31–90 daysNetwork HDD$24.502 s
Cold91+ daysObject store$4.1010 s

Using current volumes, the blended cost drops from $92.00 to roughly $19.80 per TB-month, a 78% reduction. Even with a 25% buffer for compaction overhead, we clear the 50% goal comfortably.

Note

The tier boundaries are configuration, not code. We expect to tune the hot/warm boundary per plan once we have a few weeks of production data.

Compaction pipeline

A scheduled job runs every hour. For each partition that has crossed a tier boundary, it reads the source files, merges them into files of about 512 MB, applies a heavier compression codec, and writes them to the next tier. The source is only deleted after the destination write is verified by row count and checksum. 

function compactPartition(partition, target) {
  const files = listFiles(partition);
  if (files.length === 0) return;

  // Merge small files into ~512 MB chunks
  const chunks = groupBySize(files, 512 * MB);
  for (const chunk of chunks) {
    const written = target.write(merge(chunk), { codec: "dense-9" });
    if (written.rows !== sumRows(chunk)) {
      throw new Error(`row mismatch in ${partition.id}`);
    }
  }

  markMoved(partition, target.tier);
  scheduleDelete(files, { after: "24h" });  // grace period for rollback
}

Failure handling

  1. If the write fails, the partition stays in its current tier and is retried next hour.
  2. If verification fails, the destination files are deleted and an alert is raised.
  3. Deletion of source files is delayed 24 hours so a bad compaction can be rolled back.
Warning

Compaction temporarily doubles the storage used by a partition. During the initial backfill of 12 months of data we must throttle the job to at most 40 partitions per hour, or the warm tier will run out of space.

Query routing

The router inspects the WHERE clause for a time range. If none is present, it assumes the last 30 days, matching the dashboard default. Queries that span tiers are split, run in parallel, and merged. 

SELECT country, count(*) AS visits
FROM events
WHERE site_id = 'st_4821'
  AND ts BETWEEN '2026-01-01' AND '2026-06-30'  -- spans all three tiers
GROUP BY country
ORDER BY visits DESC
LIMIT 20;
How are aggregates merged across tiers?

Each tier returns partial aggregates rather than raw rows. Counts and sums are added; averages are carried as (sum, count) pairs; distinct counts use the same sketch format in every tier so the sketches can be unioned. Exact COUNT(DISTINCT) across tiers is not supported and returns an error suggesting the approximate form.

Alternatives considered

Shorter retention on the hot cluster only

Simply deleting data after 90 days would save more money, but breaks our retention promise to customers. Rejected.

Vendor-managed tiering

Our current columnar store offers automatic tiering as a paid add-on. It would save about 35%, which misses the goal, and it moves data in fixed 7-day blocks that do not line up with our partitions.

Rollout plan

  1. Weeks 1–3: build the router behind a flag; shadow-read against the existing cluster and compare results.
  2. Weeks 4–6: enable the warm tier for internal sites only.
  3. Weeks 7–10: backfill the warm and cold tiers for all customers at the throttled rate.
  4. Week 11: switch reads to the router for all customers.
  5. Week 12: shrink the hot cluster from 48 to 14 nodes.
Point of no return

Step 5 is the only irreversible step. Before shrinking the cluster we will run a full week with the router serving 100% of reads and the old cluster still warm as a fallback.

Risks and open questions

  • Cold-tier latency variance. Object store reads have a long tail. We may need a small cache of recently read cold files.
  • Schema changes. Old partitions will have older schemas. The router must fill missing columns with nulls.
  • Open: should annual-report customers be able to pin a year of data in the warm tier for an extra fee?

Glossary

Partition
All events for one site for one day; the unit of compaction and movement.
Tier
A class of storage with its own cost and latency profile.
Compaction
Rewriting many small files into fewer large ones, usually with better compression.
Sketch
A compact probabilistic summary used to estimate distinct counts.
